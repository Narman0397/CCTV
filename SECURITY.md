# Security — v1.0.2

This document describes the security model of cctv-server v1.0.2. Every
behaviour listed here was **executed and observed** during the v1.0.2
release verification — see `docs/VERIFICATION-v1.0.2.md` for the
environment and the exact commands/results. Terminology used throughout
the docs: IMPLEMENTED / TESTED / PASS / FAIL / NOT TESTED / KNOWN
LIMITATION.

## Authentication architecture (v1.0.2)

- Passwords: **Argon2id** hashing (`cctv-core::users`), random salt per
  password via OS CSPRNG. No plaintext passwords anywhere at rest.
- Sessions: **opaque server-side tokens** (48 random bytes from `OsRng`,
  alphanumeric, generated by `state::random_token`). The **raw token is
  never stored**: the session map key is the SHA-256 of the token
  (`state::hash_token`), so a memory/DB dump never reveals a usable
  token. Expiry enforced lazily and by a periodic cleanup task.
- Cookie: `cctv_session`, `HttpOnly; SameSite=Strict; Path=/;
  Max-Age=<ttl>`, plus `; Secure` only when `auth.cookie_secure=true`.
  Tokens are **never** accepted from URLs/query strings (verified 401),
  never logged, never placed in localStorage (frontend audit).
- Auth on every `/api/*` route except the public set (`/health`,
  `/ready`, `/auth/login`, `/auth/info`) and on `/ws` (handshake checks
  session; verified 401 without, 101 with).
- JWT was **never used** in v1.0.1 (source audit: no signing/verification
  anywhere, no `jsonwebtoken` dependency). v1.0.2 **removed** all
  `JWT_SECRET` generation/config/validation/docs.

## Bootstrap admin password (P0 fix)

No default credentials exist. Flow (installer + `init`):

1. First `init` (no config password, no env var) generates a random
   24-character password from the OS CSPRNG.
2. It is printed to the console once and — only when the installer runs
   `init --password-file <path>` — written once to that file with mode
   0600 (`/etc/cctv-server/.bootstrap-admin-password` in the packaged
   install).
3. The password is immediately Argon2id-hashed into the database; the
   plaintext exists only in the operator's terminal and the 0600 file.
4. The installer displays it and **deletes the file** (best effort). The
   operator should change the password on first login.
5. Plaintext is **never** written to `secrets.env`, `config.toml`, the
   database, logs, journal or release files (verified by live test and
   release scans).

For automation, `init` accepts `CCTV_ADMIN_PASSWORD` via the environment
(transient, never persisted); unset it afterwards. Documented procedure
in `docs/INSTALL.md`.

## Rate limiting (login brute force)

IMPLEMENTED + TESTED live: per source-IP + username sliding window,
`auth.max_login_attempts` (10) failures within
`auth.rate_limit_window_seconds` (300 s) → HTTP **429** with
`retry_after_seconds`; the correct password is also refused during the
lockout; success resets the counter. Responses for "wrong password" and
"nonexistent user" are identical (no account enumeration). Limiter is
in-memory (resets on restart) — documented.

## Session lifecycle (v1.0.2)

- Login → new session (cookie + bearer token in the JSON response).
- Logout destroys the session server-side; the cookie is cleared.
- Password change invalidates **all other sessions** of that user
  (PASS: live test VERIFICATION-v1.0.2.md §D-15 + `auth_api.rs`); the current session survives.
- Session TTL enforced on every access; expired sessions evicted by a
  periodic cleanup task.
- Concurrent sessions allowed (each login creates a new session).
- No idle timeout (only absolute TTL) — documented as a KNOWN
  LIMITATION for high-security deployments.

## Network exposure

- Default bind is `0.0.0.0:8080` — intentional for LAN CCTV use.
- **Internet exposure is not recommended without a TLS reverse proxy.**
  Set `server.host = "127.0.0.1"` and proxy through nginx/caddy with TLS;
  set `auth.cookie_secure = true` when served over HTTPS.
- CORS disabled by default (`cors_allowed_origins = []`); same-origin
  dashboard.

## Media / WebSocket

- `/api/media` and `/ws` require the same authentication as the API
  (cookie or Bearer; never `?token=`).
- Media paths are canonicalized and must resolve under the configured
  recordings/snapshots directories; traversal (`/etc/passwd`, `../`,
  percent-encoded) → 403/404 (PASS: live test VERIFICATION-v1.0.2.md §D-10/11).
- Range requests supported with bounded chunking.

## RTSP / SSRF

- Only `rtsp://` URLs accepted (scheme validation, verified `file://` →
  400).
- Whitespace/control characters, `..`, backslashes rejected.
- Loopback/LAN allowed by design (CCTV sources live on the LAN); cloud
  metadata endpoints are not reachable through `rtsp://` without a local
  RTSP server, which requires API access already — not a privileged SSRF
  primitive. Documented policy.
- Credentials redacted from logs/API/status (`redact_url`,
  `redact_credentials_in_text`).
- ffmpeg spawned exclusively with **argument vectors**; no shell
  interpolation anywhere in runtime paths (audited).

## Filesystem

- All storage writes under `/var/lib/cctv-server/...`; model/recording/
  snapshot/media paths validated; symlink/absolute-path traversal blocked
  via canonicalization allow-list.

## Secrets handling (v1.0.2)

- No secrets required at runtime: sessions are opaque server-side tokens,
  passwords Argon2id. The shipped `secrets.env` (0600 root:root) is
  optional and currently contains only comments; the systemd unit still
  passes it via `EnvironmentFile=` for forward compatibility.
- `config.toml` (0640) may hold RTSP credentials for inline cameras —
  root-only, redacted in output.
- Release ZIP scanned for credentials/keys/plaintext — clean (see
  `VERIFICATION-v1.0.2.md`).

## Secret / credential rotation

- Admin password: `POST /api/auth/password` (authenticated) — all other
  sessions invalidated automatically. Then delete any leftover
  `/etc/cctv-server/.bootstrap-admin-password`.
- Camera RTSP credentials: `PATCH /api/cameras/<id>` with a new
  `rtsp_url` (or username/password fields).
- No JWT/shared secrets to rotate in v1.0.2.
- If you keep a `secrets.env` with operator keys from an older release,
  they are ignored; remove the file or rotate the values at your
  discretion.

## System hardening (systemd)

Shipped unit (`systemd/cctv-server.service`) runs as unprivileged `cctv`
with: `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`,
`PrivateTmp`, kernel/module/clock protection, `RestrictNamespaces`,
`RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6`, `SystemCallArchitectures=native`,
`UMask=0027`, empty `CapabilityBoundingSet`, `ReadWritePaths` limited to
`/var/lib/cctv-server` and `/var/log/cctv-server`,
`LimitNOFILE=65536`, `LimitNPROC=1024`, `TasksMax=512`.

Measured (v1.0.2, packaged install):

```
systemd-analyze verify /etc/systemd/system/cctv-server.service   # exit 0
systemd-analyze security cctv-server.service → Overall exposure level: 3.6 OK
```

## Abuse limits / safety

- All queues bounded (AI mpsc bounded; event bus broadcast cap 256);
  `queue_pressure_total` observed 0 under load.
- HTTP body limit 1 MB; bounded WS/message sizes (see CONFIGURATION).
- AI failure never stops recording/API/dashboard (motion-only degrade);
  model load failure handled without panic (preflight + catch_unwind).
- Logging never panics on unwritable paths (falls back to stderr).

## Threat model notes

- The dashboard is same-origin; user-controlled data is HTML-escaped
  before insertion (`esc()`); no `eval`/`Function`/`document.write`;
  tokens never in `localStorage` (audited).
- `api_error` returns generic messages without stack traces or internal
  paths.
- This document's claims map to `docs/VERIFICATION-v1.0.2.md` (PASS /
  FAIL / NOT TESTED per item).
